# 贡献与改进指南

本仓库的代码改进按固定循环执行：**分区审计 → 独立复核 → 最小实施 → 验收 → 门禁 → 提交**。
每条候选、每次改动都照本文件走，不另立流程。

## 1. 分区审计

按下列分区逐区扫描，找出结构摩擦点并产出候选卡：

| 分区 | 覆盖路径 |
|------|----------|
| 领域层 | `app/src/main/java/com/dakala/app/domain/`（model、usecase） |
| 数据层 | `app/src/main/java/com/dakala/app/data/`（local、repository、org） |
| 界面层 | `app/src/main/java/com/dakala/app/ui/`（Activity、ViewModel、components） |
| 后台层 | `app/src/main/java/com/dakala/app/worker/`、`receiver/`、`widget/` |
| 测试与文档 | `app/src/test/`、`docs/`、`README.md`、`AGENTS.md` |

卡片按所在分区编号：`<分区>-<序号>`（如 `后台层-1`）；跨区改动的按改动文件最多的区归属。

描述问题时用现成词汇，不自造术语：

- 结构问题用 `~/.agents/skills/codebase-design/SKILL.md` 的深模块词汇：module、interface、depth、seam、adapter、leverage、locality。
- 坏味道按 `~/.agents/skills/code-review/SKILL.md` 第 3 节的 Fowler 基线清单逐条对照（Duplicated Code、Shotgun Surgery、Divergent Change、Speculative Generality、Middle Man、Primitive Obsession 等 12 条）。

## 2. 候选清单与候选卡

候选卡与复核、验收记录统一落在 **`docs/IMPROVEMENTS.md`**（首次审计时创建；仓库内唯一清单，不要另开文件）。清单按分区分节，每张卡带状态：`待复核` / `已实施（<commit>）` / `已跳过（超预算）` / `驳回（原因）`。

每张卡八个字段，缺一不可：

- **位置**：`文件路径:行号`；同类重复点在多处出现时逐个列出。行号是提出时的快照，不要求随代码漂移同步维护。
- **问题**：一到三句，写可观测的危害（用户可见故障、无法写测试、改一处要动 N 处），不写「不优雅」。
- **目标形态与验收**：改完之后的结构（谁调用谁、接口长什么样），以及怎么证明达成：能写测试的给出测试名与断言要点；写不了测试的（Android 依赖、后台组件）给出可复现的手工步骤与观察点。
- **代码依据**：支撑判断的当前代码片段、行为或提交记录。
- **收益**：标注命中的项 —— leverage（调用方少学多少）、locality（改动是否收敛到一处）、可测性（测试能否跨接口写）。
- **工作量**：小 / 中 / 大，附涉及文件数。
- **改动风险**：行为是否等价、边界在哪。
- **重要度**：排序依据（如「缺陷来源」「挡住回归测试」）。

`docs/IMPROVEMENTS.md` 模板：

```markdown
# 改进候选清单

> 由《贡献与改进指南》维护：审计产出卡片，复核与验收写回同一张卡。

## 后台层-1 | 重要度 1 | 状态：待复核

- **位置**：`app/src/.../NotificationWorker.kt:124`
- **问题**：……
- **目标形态与验收**：……；验收：……（测试名 / 手工步骤与观察点）
- **代码依据**：……
- **收益**：locality（……）
- **工作量**：小（1 个文件）
- **改动风险**：……
- **重要度**：高（……）

**复核记录**：2026-10-19 <复核人/会话> —— 通过
（或：驳回，原因……；修正后通过，改了哪……）
**验收记录**：2026-10-19 —— 目标形态逐条对照：……；验证方式与结果：……；提交：`<hash>`
```

示例卡（已实施，`git show 17fcc62` 可核对）：

- **位置**：`app/src/main/java/com/dakala/app/domain/usecase/UsageStatsUseCase.kt:47`（修复前；三个零调用公开方法在 :170 / :179 / :213）
- **问题**：零调用方法留在接口上；每个入口重复「取系统服务 + 算今日区间 + queryUsageStats」样板；「今日桶过滤」有三份实现且条件不一致，锁在 private + Android 类型之后，JVM 单测无法触及。
- **目标形态与验收**：今日桶过滤抽成纯函数、查询入口收敛为一个；验收＝`UsageStatsUseCaseTest` 覆盖跨零点/越界桶边界（该提交新增，69 行）。
- **代码依据**：三份过滤各写各的边界条件，其中两份与第三份不同。
- **收益**：locality（跨天边界收敛为一处）、leverage（调用方少学一套样板）、可测性（JVM 单测可覆盖），三项全中。
- **工作量**：中（2 个文件）。
- **改动风险**：低（纯重构，行为等价）。
- **重要度**：高（已知缺陷来源，且此前无法回归测试）。

### 实施预算

- 一轮审计最多实施 **8 张卡**：按重要度取前 8 张；其余留在清单、状态改「已跳过（超预算）」。
- 「已跳过」只表示本轮不实施：下轮审计先打开 `docs/IMPROVEMENTS.md` 复核旧卡（重排重要度、剔除已被提交修掉的），再取前 8 张。
- 审计提出的候选数量不设硬上限；被独立复核驳回的卡不占预算。

## 3. 独立复核

实施前，把候选卡交给**没参与提出**的独立上下文（新的 sub-agent 会话或独立审查者）核对三问：

1. 位置与代码依据真实吗（打开文件核对）？
2. 问题描述属实吗，有无夸大？
3. 已被最近提交修掉了吗（`git log --oneline -- <path>` 核对）？

结论三态：**通过 / 驳回 / 修正后通过**；写回卡片的「复核记录」行——驳回写原因，修正后通过写改了哪一处。驳回的卡状态改「驳回（原因）」留在清单里，下轮不重复提出。

## 4. 最小实施

只做候选卡描述的改动：

- 不顺手重命名、格式化或清理无关代码；移除因本次改动而废弃的导入、变量、函数。
- 不借清理之名扩大范围：一个候选一次提交。
- 不夹带新依赖、权限、常驻开销。

## 5. 验收

实施后逐条对照候选卡，把结论写进「验收记录」行：

- **目标形态**：逐条核对是否达成；未达成写原因，不改候选卡描述来自圆。
- **收益**：确认「收益」栏每一项真的成立（locality 是否真的收敛到一处、调用方是否真的少学、测试是否真的跨接口写）。
- **验证方式**：能写测试的补 JVM 单测（放 `app/src/test/`，如 `UsageStatsUseCaseTest`）；写不了测试的按候选卡里写好的手工步骤实测并记录观察点。
- **行为等价性**：重构类改动说明为何等价；行为变更列出差异点。

门禁绿只证明没破坏，验收证明候选卡的目标真的达成——两者都要过。

## 6. 门禁

门禁命令（统一加 `--no-configuration-cache`）：

```bash
./gradlew ktlintCheck test --no-configuration-cache   # 提交前必须绿
./gradlew assembleDebug --no-configuration-cache      # 交付前（合并 main / 发版前）
```

- **改动前先记录基线**：跑一次 `./gradlew ktlintCheck test --no-configuration-cache` 并记下结果。
- **基线本来就红**：停手，先单独立项修复（另开候选卡）或经批准扩大本次范围；不得把既有红当既有事实绕过。
- **提交前必须绿**：基线绿而改后红，说明本次改动破坏了什么，就地修复，不绕过、不推迟。
- **Room schema 变更必须配套显式 `Migration`**：升 `@Database` version 或改任何实体字段时，同一提交内必须有对应 `Migration(n, n+1)` 并 `addMigrations`；`fallbackToDestructiveMigration` 仅兜未映射路径——没有迁移路径的升级会删光用户表（v1.2.0 事故），此为数据安全红线，不是可选项。
- `--no-configuration-cache` 不可省略（AGP/WorkManager 兼容性，见 `AGENTS.md`）。

## 7. 提交

约定式提交。类型表来源为本机全局 `~/.config/git/gitmessage`（feat / fix / refactor / perf / style / chore / build / ci / docs / test / revert）；header 与 body 规则如下：

```
<type>(<scope>): <subject>

<正文：为什么改>

Assisted-by: <宿主> (<模型>) <noreply@...>
```

- **subject**：动词开头、祈使语气、全小写、结尾不加句号。
- **scope**：单文件改动用文件名，多文件改动用模块名。
- **body**：空一行再写，写「为什么改」（动机、前提、取舍、未覆盖项），不重复 subject。
- **AI 协作署名**：AI 参与时补 `Assisted-by:` 尾注；NAME 按当轮 runtime 写「宿主 (模型)」，EMAIL 用该宿主的 noreply 地址；不要照抄历史提交里的署名快照。

## 克制原则

- 不新增依赖、权限、常驻开销。
- 不借清理之名扩大范围：每行改动可追溯到一张候选卡。
- 删除文件用 `trash-put`（本机冻结 `rm`），不物理删除。

## 取舍判据：删除测试

决定一个模块该留、该加深还是该删时，设想删掉它：

- 复杂度**消失**（它只是转发）→ 浅模块，候选写「删除或合并」。
- 复杂度**摊回 N 个调用方**（locality 消失）→ 值得保留，候选写「加深接口、收敛调用方」。

配套两条（源自 `codebase-design`）：

- 一个 adapter 只是假设的缝，两个 adapter 才是真的缝：不为单一实现引入 seam。
- 接口就是测试面：改完后测试写在新接口上，不绕到接口后面测内部。
